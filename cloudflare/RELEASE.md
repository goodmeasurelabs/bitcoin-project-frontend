# Release verification

PR12's public application modules were compared with the current production assets before PR13 was prepared. All application function bodies matched; differences were generated module identifiers/order, font class hashes and a Google Inter Unicode-range update. Authenticated provider settings then confirmed the same D1 binding, policy, two schedules and compatibility settings. This establishes a reconciliation baseline, not proof of a production Actions release.

The release workflow runs lint, all application/local migration tests, the OpenNext Worker build and an explicit-config Wrangler dry-run. The runtime pins include the supported Next16.4.5 security release. File-scoped warnings preserve existing client behavior for React Compiler diagnostics newly introduced by the framework update; unrelated accessibility/hook warnings remain visible.

Before publication, the workflow checks that its source is still current `main` and captures the active deployment/version for rollback. It reads only Worker settings, deployments, schedules and subdomain state. It checks the existing D1 binding identity, required policy values, relay-secret name and compatibility settings. The selected-Worker token does not manage DNS, custom domains or zone routes. Separate authenticated route/domain before/after captures are required.

After publication, sanitized metadata is written **before** preservation assertions so a failed comparison still retains the observed result. All variable hashes, binding identities, secret names, schedules and Worker URL settings must match the pre-release snapshot. A single version must serve 100% of traffic, and its version annotation must identify the exact source commit. Artifacts retain these snapshots for 30 days. The read-only manual inspection mode never publishes and cannot assert a deployed source commit.

Record the exact successful workflow run, commit, resulting Worker version, unchanged authenticated domain evidence and critical-route checks in the release evidence. A homepage HTTP200 alone does not prove source or data behavior. Test data behavior using local synthetic Miniflare D1 tests; do not submit production games, newsletter requests, email or analytics events as release tests. Preserve newsletter sending disabled and the existing migration control state. Do not query or write production D1, run migrations/imports, rotate secrets, create resources, change DNS/MX, or disconnect rollback hosting as part of this release.
